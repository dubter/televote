# Televote — технический дизайн

Анонимное голосование под пик ТВ-эфира. Один вопрос, окно 60 секунд, без регистрации.

| | |
|---|---|
| Зрителей | 100 млн |
| Окно голосования | 60 с |
| Расчётная конверсия | 30 % → **30 млн голосов** |
| Пик | **~2M RPS** на `/vote` и столько же на `/ballot` |
| Ёмкость | ~100 инстансов (4 vCPU), Redis Cluster 32+32, Postgres 1+1 |

---

## 1. Пять решений

| Решение | Почему |
|---|---|
| Голос — инкремент, не строка | нужен агрегат; 30 млн голосов = счётчики, не записи |
| Read-path целиком на CDN | опрос один для всех; иначе 30 млн запросов за одним JSON убьют origin |
| Один голос = один Lua-вызов | дедуп и инкремент атомарно → корректность + идемпотентный ретрай |
| Шардирование по `voter_id` с hash tag | дедуп и счётчик в одном слоте; нагрузка размазана по кластеру |
| Ёмкость по расписанию, не автоскейлинг | событие короче петли обратной связи HPA |

---

## 2. Нагрузка

Конверсия ТВ-рекламы обычно — доли процента. Считаем под 30 %: архитектура масштабируется линейно, ёмкость выделяется под конкретный эфир.

| Сценарий | Конверсия | Голосов | Пик |
|---|---|---|---|
| На практике | 1 % | 1 млн | ~60k RPS |
| Оптимистично | 5 % | 5 млн | ~300k RPS |
| **Расчётный** | **30 %** | **30 млн** | **~2M RPS** |

Половина трафика — в первые 15 секунд: `15 млн / 15 с ≈ 1M RPS` средних, пик ~2M.

### Что доходит до origin

| Запрос | Кэш | На origin |
|---|---|---|
| `GET /p/{slug}` — страница | immutable, CDN | ~0 |
| `GET /api/v1/polls/{slug}` — вопрос | TTL 10 с, CDN | ~0 |
| `POST …/ballot` | нет | 2M RPS |
| `POST …/vote` | нет | 2M RPS |

Токен нельзя отдавать вместе с конфигом: ответ станет некэшируемым и 30 млн запросов придут на бэкенд.

**Вес страницы — архитектурное ограничение.** Лишний КБ = 30 ГБ трафика за минуту. Один документ без внешних ресурсов, ~8 КБ gzip.

### Ёмкость

```
приложение   /vote  30–50k RPS/инстанс · /ballot 80–120k → ~100 инстансов
Redis        Lua однопоточный, 60–100k EVALSHA/s на мастер → 32 мастера + 32 реплики
дедуп        30 млн × ~100 Б ≈ 3 ГБ → 94 МБ на мастер
AOF за эфир  ~2.1 ГБ → 66 МБ на мастер
Postgres     единицы RPS, вне горячего пути
```

Датасет на ноду не растёт: делится на число мастеров, которое растёт вместе с нагрузкой. Поэтому `fork` остаётся дешёвым.

## 3. Архитектура

```
зритель → CDN ─┬─ страница, конфиг опроса (кэш)
               └─ POST /ballot, /vote → LB → app ×100 (stateless)
                                               ↓ EVALSHA, 1 RTT
                                        Redis Cluster 32+32
                                               ↓ снапшот 5 с, чтение с реплик
                                        Postgres (primary + replica)
```

| Слой | Что | Статус |
|---|---|---|
| L0 браузер | одна кнопка, `localStorage` как UX | клиент |
| L1 CDN edge | статика, конфиг, выдача токенов | описан |
| L2 vote service | валидация, rate limit, Lua-вызов | реализуем |
| L3 Redis Cluster | дедуп + счётчики | реализуем |
| L4 Postgres | control plane | реализуем |

`/ballot` не имеет состояния → переносится на edge и снимает половину запросов с origin. При 2M RPS это не опция, а необходимость.

### Redis = data plane, Postgres = control plane

| | Data plane | Control plane |
|---|---|---|
| RPS | ~2 000 000 | единицы |
| Данные | счётчики, эфемерный дедуп | опросы, пользователи, история |
| Запросы | инкремент по ключу | список, фильтры, пагинация |
| Жизнь | минуты | годы |

Postgres нужен ради: вторичных индексов админки, транзакции «опрос + N опций + уникальный slug», холодных данных вне RAM, версионированной схемы, независимого носителя. Без админки он был бы не нужен.

### Пакеты

```
domain      Poll, Option, валидация голоса, FSM         зависит: ни от чего
ballot      HMAC-токены                                 domain
vote        Lua, деривация ключей, шардирование         domain, Redis
snapshot    перенос агрегата в Postgres                 Redis, Postgres
storage/pg  репозитории control plane                   pgx
httpapi     хендлеры, middleware                        всё выше
observ.     OTel, метрики, логи, health                 —
```

## 4. Горячий путь

### Lua: дедуп и инкремент одной операцией

```lua
-- KEYS[1] = v:{p:<pollID>:s<shard>}:<voterID>   маркер дедупа
-- KEYS[2] = c:{p:<pollID>:s<shard>}             хэш счётчиков
-- ARGV[1] = ttl, ARGV[2..] = индексы опций
if redis.call('SET', KEYS[1], '1', 'NX', 'EX', ARGV[1]) == false then
  return 0
end
for i = 2, #ARGV do redis.call('HINCRBY', KEYS[2], ARGV[i], 1) end
redis.call('HINCRBY', KEYS[2], 'b', 1)
return 1
```

| Свойство | Откуда |
|---|---|
| Корректен при любой балансировке | Redis — единственный авторитет, sticky routing не нужен |
| Нет гонки «дедуп есть, счётчик нет» | Lua не вытесняется |
| **Ретрай идемпотентен** | дедуп-ключ = idempotency key |
| 1 RTT вместо 2 | проверка и запись слиты |

Идемпотентность несущая: на ней держатся ретрай клиента при таймауте и синхронный ретрай сервера при сбое шарда.

### Шардирование

```
shard = xxhash64(voterID) % poll.shard_count
tag   = {p:<pollID>:s<shard>}       → оба ключа в одном слоте, иначе CROSSSLOT
```

Ключ шардирования не выбирается: дедуп привязан к `voter_id`, атомарность требует общего слота. `voter_id` из `crypto/rand` → распределение равномерное.

**`shard_count` не константа.** Перекос между мастерами = `1/√(шардов на мастера)`:

| Шардов на мастера | 32 | 128 | 512 | 1024 |
|---|---|---|---|---|
| Перекос | ±17 % | ±8.8 % | ±4.4 % | ±3.1 % |

Правило: `shard_count ≈ 500 × мастеров`, потолок 16384 (гранулярность слотов). Значение **фиксируется в строке опроса** — смена константы в эфире перевела бы проголосовавших на другие шарды и открыла повторное голосование.

### Consistent hashing не нужен

Redis Cluster уже делает то же самое лучше: 16384 слота — фиксированное пространство, отвязанное от числа нод, плюс явная таблица назначений (включая неравные доли). Наш `% shard_count` — не число нод, а константа fan-out.

Единственная опасность — смена константы; кольцо её не лечит, а лишь уменьшает долю сломанных с ~всех до 1/N. Для дедупа этого недостаточно.

> Consistent hashing **требовался** в отвергнутом варианте с дедупом в памяти инстанса — там нужен был sticky routing, кольцо менялось при scale-out и дедуп ломался на пике. Перенос дедупа в Redis снял требование.

### Чтение результатов — O(1)

```
snapshotter (5 с)  HGETALL × shard_count с реплик → свёртка → agg:{pollID}
/results                         1 × HGETALL agg:{pollID}
```

Fan-in делается раз в интервал и на репликах — не делит мультиплекс с записями.

## 5. Дедупликация

ТЗ: «достаточная на уровне обычных пользователей», антифрод не требуется.

| Слой | Механизм | Останавливает | Обходится |
|---|---|---|---|
| 0 | `localStorage` | двойной клик, F5 | за 2 секунды |
| 1 | HMAC-токен | подделку | легальным получением нового |
| 2 | дедуп в Redis | повтор тем же токеном | новым токеном |
| 3 | rate limit по подсети | наивный скрипт | прокси, ботнетом |
| — | окно `opens_at`/`closes_at` | голоса вне эфира | — |

HMAC защищает от подделки токена, не от массового легального получения. Слои останавливают человека с F5 и инкогнито, не останавливают двадцать строк на Python.

### Токен

```
payload = pollID(16) ‖ voterID(16) ‖ exp(uint32) ‖ keyID(1)
token   = base64url(payload) '.' base64url(HMAC-SHA256(secret, payload))
```

~110 байт против ~300 у JWT → при 30 млн выдач экономия ~6 ГБ трафика.

- `voterID` — 128 бит из `crypto/rand` (64 дали бы коллизии при 30 млн)
- `pollID` в payload и проверяется
- сравнение только `hmac.Equal`
- **два активных ключа** — ротация в эфире иначе инвалидирует все выданные токены

### Инварианты

```
ttl(dedup) ≥ exp(token) + clock_skew     иначе окно для replay
ttl получает джиттер ±10 %               иначе 30 млн ключей истекут разом
```

Проверяются тестом и при старте сервиса.

### Антинакрутка сверх дедупа

Скрипт накручивает 1 % за несколько долларов: `/ballot` бесплатен, а лимит по IP обязан быть щадящим из-за CGNAT. ТЗ этого и не запрещает, но контекст «национальная компания» повышает цену ошибки, поэтому добавлены два дешёвых слоя вне горячего пути.

**Фильтр датацентровых ASN.** Зритель ТВ голосует с мобильного или домашнего IP; голос с AWS, Hetzner или DigitalOcean по определению не зритель. Готовая база префиксов, проверка при выдаче токена.

**Детект аномалий.** Асинхронно, сэмплом 1 %, в отдельные ключи:

```
anom:{pollID}:net    HINCRBY по /16-подсети
anom:{pollID}:fp     HINCRBY по хэшу fingerprint
```

Ничего не блокирует, но показывает, что 40 % голосов пришли из одной автономной системы — этого достаточно, чтобы результат не выпустить в эфир. **Анонимность не страдает:** агрегат по подсети человека не идентифицирует, а связи с конкретным голосом нет.

| Слой | Стоимость накрутки 1 % |
|---|---|
| Только rate limit | ~$5 |
| + ASN-фильтр | ~$10–20 |
| + детект аномалий | не мешает, но накрутка видна |
| + Turnstile (не берём) | ~$500 |

Turnstile описан как следующий шаг: он единственный меняет порядок цены, но добавляет зависимость от Cloudflare.

### Rate limit — три ошибки, которые легко сделать

| Ошибка | Последствие |
|---|---|
| Лимит количества, а не частоты | за CGNAT сотни тысяч человек — режем целевую аудиторию |
| Лимит по полному IPv6-адресу | у клиента /64, каждый запрос с нового адреса → защиты нет |
| `X-Forwarded-For` как есть | обход одной строкой в curl |

Главная цель лимита — `/ballot`, а не `/vote`: выдача токенов и есть вектор.

## 6. Данные

### Postgres

```sql
polls        (id, slug unique, question, type, min_choices, max_choices,
              status, opens_at, closes_at, shard_count,
              results_visible_during_voting, version, created_at)
poll_options (poll_id, idx smallint, text)          -- PK (poll_id, idx)
poll_results (poll_id, option_idx, votes, updated_at)
poll_stats   (poll_id, ballots_total, updated_at)
admin_users  (id, login, password_hash, role)
admin_audit  (id, actor, action, entity, payload, at)
```

Опция адресуется целым индексом, не UUID → счётчик становится полем хэша, payload голоса `{"choices":[2]}`.

Проценты считаются от `ballots_total`, не от суммы голосов — при множественном выборе сумма больше числа проголосовавших.

FSM: `draft → scheduled → open → closed → archived`. Статус хранится явно, не выводится из дат — иначе состояние зависит от часов машины.

### Redis

```
c:{p:<pollID>:s<shard>}         hash {"0":1249, "1":883, "b":2132}
v:{p:<pollID>:s<shard>}:<voter> "1" с TTL — дедуп
agg:{pollID}                    свёрнутый результат
```

### Как данные попадают в Postgres

Не поток и не очередь: снапшотер **периодически пересчитывает полное состояние** — читает абсолютные значения, пишет абсолютные. Отсюда: пропущенный цикл догоняется, порядок не важен, повтор безвреден.

```
каждые 5 с:
  1. HGETALL по всем шардам, с реплик (DoMulti, один пайплайн)
  2. свёртка в памяти: votes[idx] += v, ballots += b
  3. монотонность: max(посчитанное, последнее известное)   ← одно место
  4. HSET agg:{pollID}          → /results читает одну команду
  5. UPSERT ... GREATEST        → Postgres
```

```sql
ON CONFLICT (poll_id, option_idx)
DO UPDATE SET votes = GREATEST(poll_results.votes, excluded.votes)
```

`GREATEST` даёт неожиданное: счётчики монотонны → два снапшотера одновременно безопасны → лидер-элекшн становится оптимизацией, а не требованием корректности.

**Дедуп-ключи в Postgres не едут никогда.** Переносится только агрегат.

Направление данных строго одностороннее — Redis ничего не получает от Postgres:

```
создание опроса   админка → Postgres (транзакция)
открытие          админка → Postgres
голосование       app → Redis                                  Postgres не участвует
конфиг            Postgres replica → память инстанса, фоном раз в 2 с
агрегация 5 с     Redis (реплики) → agg: + Postgres
чтение в эфире    agg:{pollID}                                 свежесть ≤5 с
чтение после      poll_results из Postgres                     финальный
закрытие +30 с    финальный цикл → status='closed'
```

Снапшот неатомарен между шардами — для монотонных счётчиков это значит «не больше реального».
Финальный снапшот с задержкой 30 с, иначе теряется хвост голосов в буферах.

## 7. API

| Метод | Путь | Кэш | Заметки |
|---|---|---|---|
| `GET` | `/p/{slug}` | immutable | статика |
| `GET` | `/api/v1/polls/{slug}` | TTL 10 с | вопрос, опции, `server_time` |
| `POST` | `…/ballot` | нет | выдаёт токен |
| `POST` | `…/vote` | нет | принимает голос |
| `GET` | `…/results` | TTL 1 с | если разрешено |

**`/ballot` обязан быть POST** — GET префетчится браузерами и мессенджерами при развороте превью.
**`server_time` в конфиге** — клиент работает по серверному времени, иначе сбитые часы ломают голосование.

### Ответы `/vote`

| Код | Тело | Когда |
|---|---|---|
| 200 | `counted` | принят |
| 200 | `already_counted` | **дубль тем же токеном** |
| 400 | `invalid_choices` | нарушены `min/max`, неверный индекс |
| 401 | `invalid_token` | подпись, `exp`, чужой `poll_id` |
| 409 | `poll_closed` | вне окна |
| 429 | — | rate limit |
| 503 | `Retry-After` | буфер переполнен |

**Дубль — 200, не 409.** При таймауте клиент не знает, дошёл ли голос; ретрай вернёт «дубль», и ошибка показала бы отказ человеку, чей голос учтён. Накрутке 200 ничего не даёт — счётчик не растёт.

Админский API: `POST /admin/polls`, `GET /admin/polls`, `…/{id}/open`, `…/{id}/close`, `…/{id}/results`.
JWT с коротким TTL, пароли argon2id, роли admin/editor/viewer, все действия в `admin_audit`.

## 8. Отказоустойчивость

Требование: падение любого одного компонента не выводит систему из строя.

### Конфиг опроса не должен быть на горячем пути

Каждому голосу нужны `shard_count`, `closes_at`, `type`, `min/max_choices`, секрет опроса. Читать их из хранилища на каждый голос нельзя: 2M RPS в Postgres невозможны, а лишний вызов Redis удвоил бы нагрузку на кластер.

Конфиг неизменяем после открытия (правка опций запрещена), поэтому живёт в памяти процесса:

```
Postgres replica ──фоновый рефрешер, раз в 2 с──► map в памяти инстанса
```

Фоновое обновление, а не ленивый TTL: при 2M RPS истечение TTL дало бы thundering herd из тысяч одновременных промахов. **Горячий путь читает только память и никогда не блокируется.**

Стоимость: 100 инстансов × раз в 2 с = 50 запросов/с к реплике. Чтение идёт с реплики, поэтому failover primary (10–60 с у Patroni) блокирует только админку, а голосование его не замечает.

### Таблица отказов

| Компонент | Экз. | Падение одного | Деградация |
|---|---|---|---|
| CDN PoP | сотни | трафик на соседний | нет |
| Балансировщик | managed, N зон | зона выпадает | нет |
| Инстанс приложения | ~100 | трафик перетекает | нет, stateless |
| Redis master | 32 | реплика промотится ~8 с | голоса шарда **буферизуются** |
| Redis replica | 32 | чтение уходит на мастера | нагрузка мастера ↑ |
| Postgres primary | 1+1 | failover | админка; **голосование идёт** |
| Snapshotter | N, лидер | другой подхватывает | архивация на цикл |
| Телеметрия | 1 | слепота | нет |

Единственная жёсткая зависимость — Redis Cluster целиком. Отказ отдельной ноды система переживает.

### Голос не покидает запрос

Первая версия дизайна складывала голоса недоступного шарда в очередь в памяти инстанса и отвечала клиенту 200. Это ошибка: буфер живёт в волатильной памяти в единственном экземпляре, OOM или `SIGKILL` при выкатке уносят его целиком — **и мы уже сказали человеку, что голос учтён**. `Drain` при `SIGTERM` спасает от плановой остановки и не спасает от остальных.

Вместо буфера — синхронный ретрай с коротким бюджетом и честный отказ:

```go
const retryBudget = 250 * time.Millisecond

ctx, cancel := context.WithTimeout(ctx, retryBudget)
for attempt := 0; ; attempt++ {
    if breaker.Open() { return ErrUnavailable }     // кластер лежит — не копим соединения
    res, err := caster.Cast(ctx, ...)
    if err == nil { return res }
    if !vote.IsRetryable(err) { return err }
    if !sleepWithJitter(ctx, attempt) {            // 20мс, 60мс, 150мс
        return ErrUnavailable                       // → 503 Retry-After
    }
}
```

**Голос хранит браузер.** Он не словит OOM от нашего пика и не перезапустится при нашей выкатке. Токен у клиента уже есть, ретрай идемпотентен по `voter_id`:

```js
for (let i = 0; i < 6; i++) {
  const r = await post("/vote", {token, choices});
  if (r.status !== 503) return r;
  await sleep(400 * 2**i * (0.5 + Math.random()));   // джиттер обязателен
}
```

Шесть попыток покрывают ~25 секунд. Джиттер здесь не украшение: без него все клиенты недоступного шарда ретраят синхронно и добивают реплику в момент промоушена.

**Circuit breaker обязателен.** Без него падение всего кластера держит `2M RPS × 250 мс = 500 000` открытых запросов, и мы умираем сами.

| | Буфер на сервере | Ретрай клиентом |
|---|---|---|
| Переживает OOM инстанса | нет | **да** |
| Переживает `SIGKILL` при выкатке | нет | **да** |
| Честность ответа | врём 200 | честный 503 |
| Состояние на сервере | есть | **нет** |
| Человек видит, что идёт повтор | нет | да |

Практика это подтверждает: для пути записи рекомендуется логировать и ретраить, **а не буферизовать локально**.

### Managed Redis непригоден

ElastiCache делает автоматический failover **за 60–120 секунд**, и AWS не даёт SLA на RTO; всё это время приложение видит ошибки соединения. **Наш эфир длится 60 секунд** — то есть при managed-решении упавший шард мёртв весь эфир и ещё минуту после, и никакой клиентский ретрай этого не покрывает.

Отсюда жёсткое ограничение: **self-hosted Redis Cluster с настраиваемым таймаутом, а не ElastiCache или Memorystore.**

### WAIT не берём

| | Масштаб |
|---|---|
| Потеря данных при failover | ~62 голоса (62.5k RPS × 1 мс lag) |
| **Недоступность шарда во время failover** | 5–8 с × 62.5k = **до 500 тыс. голосов** |
| Отказ мастера **без реплики** | весь шард за эфир ≈ 940 тыс. |

WAIT лечит первую строку — 0.0002 % — удваивая число мастеров, и гарантии всё равно не даёт (Redis без консенсуса на запись). Вторую закрывает буфер, третью — обязательная реплика с anti-affinity по AZ.

`cluster-node-timeout = 5000`: недоступность шарда ~8 с вместо ~30 при дефолте.

Это осознанное отклонение от практики. Общая рекомендация — не меньше 15 секунд в облаке, потому что короткий таймаут вызывает ложные failover на сетевых заминках, а ложный failover на пике обходится дороже настоящего. Пять секунд взяты потому, что окно эфира всего 60 секунд, а инфраструктура на это время выделенная и прогретая. **Проверяется нагрузочным тестом: если ложные срабатывания появятся, порог поднимается до 10–15 секунд** — клиентский ретрай покрывает и такой простой.

### Валидация — тестом, не декларацией

Каждый сценарий заканчивается проверкой **корректности агрегата**, а не «сервис отвечает».

| Сценарий | Ожидание |
|---|---|
| `make chaos-redis-master` | failover прошёл; доля 503 выросла и вернулась к нулю; **сумма счётчиков сходится с числом ответов `counted`** — значит клиенты догнали |
| `make chaos-app` | трафик перетёк, дедуп ловит повтор на другом инстансе |
| `make chaos-postgres` | голосование идёт, снапшоты возобновляются |
| `make chaos-latency` | p99 растёт, потерь нет, буфер дренируется |

## 9. Масштабируемость и узкие места

| Компонент | Ограничение | Масштабируется | Характер |
|---|---|---|---|
| CDN | — | managed | потолка нет |
| Балансировщик | pps, соединения | managed, N зон | линейно |
| Приложение | syscalls | горизонтально, stateless | линейно |
| Redis: пропускная | **однопоточный Lua** | добавлением мастеров | линейно |
| Redis: память | дедуп-ключи | тем же шардированием | линейно |
| Чтение результатов | fan-in по шардам | пред-агрегация | O(1) |
| Postgres | вне горячего пути | вертикально + реплики | не узкое место |

**Главный потолок — однопоточность Lua.** 60–100k/s на мастер независимо от числа ядер: вертикальное масштабирование Redis не работает вообще, только добавление мастеров. Зато линейно, и датасет на ноду падает вместе с этим.

Узкие места, которые надо назвать заранее:

- **Логи и трейсы** — при 2M RPS запись на каждый запрос это терабайты. Сэмплирование не оптимизация, а условие работы.
- **Rate limiter** — LRU по IP при десятках млн адресов. Размер таблицы ограничивается явно.
- **Аллокации** — лишняя аллокация на запрос = 2 млн/с. `sync.Pool`, никаких лишних `string`↔`[]byte`.
- **Вес страницы** — лишний КБ = 30 ГБ за минуту.
- **Выдача токенов** — 2M RPS, столько же сколько голосов. Перенос на edge обязателен.

## 10. Планирование ёмкости: почему не автоскейлинг

| Этап петли HPA | Время |
|---|---|
| scrape + окно усреднения | ~45 с |
| sync loop | 15 с |
| **rate limiter `100 %/15 с`**: 10→20→40→80→160 | 60 с |
| провижининг нод (EKS) | 40–120 с |
| pull, старт, readiness | 10–40 с |

От «нагрузка пришла» до «под принимает трафик» — минимум 60 с, реалистично 2–3 минуты. **Ролик длится 60 секунд, пик в первые 15.** Автоскейлер добавит мощности под трафик, которого уже нет, и погасит их через 5 минут.

Redis не масштабируется в эфире вовсе: миграция слота с миллионами ключей идёт минутами, клиенты получают `ASK`/`MOVED` на пике.

**Нагрузка не стохастическая — слоты покупаются заранее.** Управляющий вход это календарь:

```
T-15 мин   scheduled scale-out, прогрев пулов
T-5  мин   gate: N подов Ready, кластер healthy, синтетический голос проходит
T-0        эфир
T+60 с     конец
T+10 мин   scale-in
```

HPA остаётся страховкой: scheduled задаёт `minReplicas`, HPA только добавляет. Scale-down в окне запрещён явно.

**Сигнал для HPA — не CPU.** Сервис I/O-bound: горутины блокируются на сети, CPU низкий, HPA доложит «всё спокойно», пока p99 улетает. Сигналы: запросы в полёте, латентность Redis, доля 429/503, частота открытий circuit breaker.

Время старта:

- **pause-поды** держат ноды тёплыми — убирают провижининг из критического пути
- образ предзагружен
- `readinessProbe` реально проверяет Redis, иначе под встанет Ready и начнёт отдавать ошибки
- пулы прогреваются до readiness
- Go стартует за миллисекунды, JIT-прогрева нет

Экономика: ~100 инстансов и 64 ноды Redis на 20 минут вокруг эфира. Три ролика в неделю = час пиковой ёмкости против 168 часов. Держать постоянно дороже в ~170 раз.

## 11. Безопасность

| Область | Меры |
|---|---|
| Админка | argon2id, JWT с коротким TTL + refresh, RBAC, аудит. Дефолтные креды — **ошибка старта** при `ENV=production` |
| Ballot | HMAC-SHA256, посекретный на опрос, `hmac.Equal`, `exp`, привязка к `poll_id`, ротация двумя ключами |
| DoS | `MaxBytesReader` 1 КБ, `ReadHeaderTimeout` против Slowloris, `LimitListener`, circuit breaker, строгий лимит на `/ballot` |
| Заголовки | HSTS, CSP без inline, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, CORS по allowlist |
| Сборка | `gosec`, `govulncheck`, Dependabot, distroless, non-root, read-only rootfs |
| Инъекции | параметризованные запросы pgx; в Lua только `KEYS`/`ARGV` |

**Приватность — свойство конструкции, не декларация.** Дедуп-ключ хранит факт голосования, но не выбор: восстановить «кто за что» невозможно. `voter_id` из `crypto/rand`, не производный от IP. IP в логах только хэшем с ротируемой солью. TTL = автоматическое стирание следов.

## 12. Наблюдаемость

Всё по OTLP в единое окно Grafana (`grafana/otel-lgtm` = Grafana + Prometheus + Loki + Tempo + Collector в одном контейнере).

| Сигнал | Транспорт |
|---|---|
| Метрики | OTel SDK → OTLP, плюс `/metrics` для прода |
| Трейсы | OTel SDK → OTLP, `ParentBased(TraceIDRatioBased(0.0001))` |
| Логи | `slog` → OTel bridge → OTLP, плюс stdout JSON |
| Ошибки | structured error-логи + `errors_total{type}`; Sentry опционален |

При 2M RPS нельзя логировать и трейсить каждый запрос. Полноту даёт не лог, а метрики.

Ценность — корреляция: `trace_id` ведёт с графика 5xx через exemplar в трейс упавшего голоса, оттуда в логи и обратно.

Дашборды в репозитории (provisioning):

1. **Overview** — RPS, accepted/rejected по причинам, p50/p95/p99, in-flight, ошибки
2. **Redis** — ops/s по нодам, `latest_fork_usec`, `aof_delayed_fsync`, **`evicted_keys` (обязан быть 0)**, память, **распределение по шардам**
3. **Errors & Traces** — error rate по типам, логи, переходы в Tempo

Панель распределения по шардам эмпирически доказывает, что шардирование работает и горячего ключа нет.

## 13. Корнер-кейсы

### Семь тихих отказов

Ломают корректность, не оставляя следа ни в тестах, ни в логах, ни на дашборде.

| Отказ | Последствие | Защита |
|---|---|---|
| `maxmemory-policy` ≠ `noeviction` | Redis вытесняет дедуп → повторы идут в счёт | конфиг + алерт `evicted_keys > 0` |
| `ttl(dedup) < exp(token)` | окно легального replay | инвариант в тесте и на старте |
| Интеграционные тесты на одиночном Redis | `CROSSSLOT` не воспроизводится, падает в проде | testcontainers поднимает **кластер** |
| Rate limit по полному IPv6 | у клиента /64 — защиты нет, метрика зелёная | лимит по префиксу |
| `X-Forwarded-For` без доверенного прокси | обход одной строкой в curl | только hop от своего ingress |
| Лавинное истечение TTL | active expiry молотит на хвосте голосования | джиттер ±10 % |
| `fork` на AOF rewrite в пик | задержка сотни мс | `auto-aof-rewrite-percentage 0` в окне |

### Клиент

| Кейс | Решение |
|---|---|
| Двойной клик | второй → `200 already_counted` |
| Таймаут в мобильной сети | ретрай **тем же токеном**; новый = новый `voter_id` = двойной голос |
| Страница открыта за два часа | токен протух → перезапрос и повтор один раз |
| Часы клиента врут | работа по `server_time` |
| Safari private / ITP | `localStorage` бросает — всё в try/catch |
| Webview мессенджера | часто нет storage → серверный дедуп |
| JS отключён | осмысленный `<noscript>` |
| bfcache при «назад» | проверка на `pageshow` |
| Префетч ссылки | `/ballot` только POST |
| Инкогнито | новый `voter_id`, голос засчитан — by design |

### Redis

| Кейс | Последствие |
|---|---|
| Failover на пике | теряется незареплицированное (~62 голоса); остальное догоняет клиентский ретрай |
| Split-brain | `full-coverage no`: теряется доля, не весь опрос |
| Head-of-line blocking при чтении | чтение результатов с реплик |
| `NOSCRIPT` после failover | rueidis фоллбэчит на `EVAL` |
| Ошибка в середине Lua | Redis не откатывает; реалистичная причина — OOM |
| Slot migration в эфире | запрещено регламентом |

### Агрегация и админка

| Кейс | Решение |
|---|---|
| Два снапшотера одновременно | `GREATEST` делает безопасным |
| Хвост голосов после `closes_at` | финальный снапшот через 30 с |
| Redis потерял данные при failover | `GREATEST` не даёт откатить назад |
| Правка опций после первого голоса | запрещена — меняет смысл поданных голосов |
| Два админа редактируют | optimistic locking по `version` |
| Статус выводится из дат | нет: явный FSM |
| **Публичные результаты в эфире** | флаг, **default false** — промежуточный счёт влияет на непроголосовавших и портит опрос |

### Эксплуатация

| Кейс | Решение |
|---|---|
| Rolling update в эфире | freeze window |
| `preStop` короче дренирования LB | `preStop sleep` + больший grace |
| Ретраи после восстановления шарда | джиттер в клиенте разводит их во времени |
| Connection storm при старте | мультиплексирование rueidis |
| Ролик вышел не по плану | кнопка немедленного scale-out |
| Несколько роликов сразу | ёмкость по сумме активных опросов |

## 14. Трейд-оффы

| Развилка | Выбор | Чем платим |
|---|---|---|
| Дедуп в памяти vs Redis | **Redis** | +1 RTT, жёсткая зависимость |
| Атомарность vs раздельные хранилища | **атомарность** | дедуп и счётчики делят память кластера |
| `cluster-require-full-coverage` | **no** | теряем долю вместо всего опроса |
| WAIT | **не берём** | ~62 голоса при failover |
| `cluster-node-timeout` | **5 с** | редкие ложные срабатывания |
| Persistence Redis | **AOF everysec везде** | ~0; rewrite отключён в окне |
| Redis недоступен | **синхронный ретрай 250 мс, потом 503** | человек видит паузу; голос хранит браузер |
| Managed vs self-hosted Redis | **self-hosted** | своя эксплуатация кластера |
| Fallback-шард при отказе | **нет** | простой шарда покрывается клиентским ретраем |
| Дедуп | **точные ключи** | 3 ГБ вместо 54 МБ у Bloom, зато ноль ложных отказов |
| Аудит-трейл голосов | **нет** | результат неоспорим и неисправим |
| Kafka на горячем пути | **нет** | нет replay и пересчёта |
| Дубль → 409 или 200 | **200 + флаг** | не отличить свой ретрай от повторной попытки |
| Rate limit | **локальный** | порог = N × локальный, плывёт при скейлинге |
| Один Redis vs Redis + Postgres | **оба** | +1 хранилище ради control plane |
| Fan-in на чтении vs пред-агрегация | **пред-агрегация** | результат отстаёт на 5 с |
| `shard_count` | **≈500 × мастеров** | подбирается при создании опроса |
| Трейсинг всех запросов | **сэмпл 0.01 %** | единичный сбой может не попасть |
| k8s-манифесты | **нет** | рассуждение вместо непроверенного YAML |

## 15. Поддерживаемость

```
domain  ◄──  application  ◄──  adapters (http, redis, postgres)
```

`domain` не импортирует ничего из проекта. Обратные импорты запрещены **линтером** (`depguard`), не соглашением.

| Что | Правило |
|---|---|
| Конструкторы | `New*(deps…) (*T, error)`, зависимости параметрами, без глобалов и `init()` |
| Ошибки | типизированные доменные, **единственная** точка маппинга в HTTP |
| Логи | `slog`, общий набор атрибутов, `trace_id` везде |
| Контекст | `ctx` первым, таймаут на каждом внешнем вызове |
| Интерфейсы | на стороне потребителя, узкие |
| Конфиг | одна структура с тегами, валидация при старте, fail fast |

Единственная точка маппинга ошибок — не стилистика: она гарантирует, что `already_counted` вернёт 200 из любого хендлера, а не 409 из написанного последним.

CI: `golangci-lint` (`errcheck`, `govet`, `staticcheck`, `revive`, `gocritic`, `gosec`, `bodyclose`, `contextcheck`, `nilerr`, `depguard`), `govulncheck`, `go test -race`, порог покрытия.

Тесты table-driven, имена читаются как утверждения: `TestVote_DuplicateTokenReturnsAlreadyCounted`. Интеграционные — на настоящих Redis Cluster и Postgres.

Комментарии объясняют «почему»: почему дубль возвращает 200, почему `shard_count` привязан к опросу, почему `GREATEST` снимает требование лока.

## 16. Что осознанно не покрыто

- **Накрутку ботнетом не останавливаем** (по ТЗ и не должны). Обнаруживать можно без нарушения анонимности: агрегат по /16-подсетям показывает аномальное распределение. Готовое расширение.
- **Результат нечем защитить в споре** — следствие отказа от аудит-трейла.
- **Real-time на студийном экране** потребовал бы SSE и другого профиля чтения.
- **Мультирегиональность** — один регион; глобальное распределение это L1/edge.

## 17. Стенд

```
redis-1..6      redis:8-alpine, кластер 3 мастера + 3 реплики, AOF everysec
redis-init      one-shot: redis-cli --cluster create --cluster-yes
postgres        postgres:17-alpine, healthcheck pg_isready
migrate         one-shot: goose up
app-1, app-2    два инстанса — мультиинстансность не на словах
nginx           LB на :8080, проставляет X-Real-IP
otel-lgtm       Grafana :3000, приём OTLP :4317
redis-exporter  метрики Redis
k6              профиль load
```

Порядок старта детерминирован через `service_healthy` и `service_completed_successfully`. Хост-порты через `${VAR:-default}` — конфликт портов вторая по частоте причина, по которой «одна команда» не срабатывает.

```
make demo    поднять всё, дождаться готовности, создать опрос, напечатать ссылки
make smoke   end-to-end проверка
make load    k6
make chaos   сценарии отказов
make test    unit + integration (testcontainers, Redis Cluster)
```

### Smoke доказывает главное требование

```
1. создать опрос
2. взять токен на app-1
3. проголосовать на app-1        → counted
4. тем же токеном на app-2       → already_counted   ← дедуп не зависит от инстанса
5. /results                      → ровно один голос
6. после closes_at → 409, испорченная подпись → 401
```

### Нагрузочный тест

Ноутбук не выдаст 2M RPS. k6 меряет **стоимость одного голоса**: CPU-мс на инстанс, команд в Redis, байт по сети, аллокаций. Из неё ёмкость считается линейно — это то число, которое идёт в плановое масштабирование.

Плюс проверка корректности: **сумма счётчиков = число успешных ответов**. Тест на латентность такую потерю не увидел бы.

**Пишем сами:** Lua-скрипт (бизнес-логика), деривация ключей (~10 строк), write-behind буфер (bounded channel), ballot-токен (~40 строк ради 110 байт вместо 300 у JWT).

`rueidis` выбран за auto-pipelining конкурентных запросов и мультиплексирование соединений — батчинг под нагрузкой достаётся бесплатно, connection storm при старте подов не возникает.
