# Televote — технический дизайн

Анонимное голосование под пик ТВ-эфира. Один вопрос, окно 60 секунд, без регистрации.

| | |
|---|---|
| Зрителей | 100 млн |
| Окно голосования | 60 с |
| Расчётная конверсия | 30 % → **30 млн голосов** |
| Пик приёма | **~2M RPS** на единственную ручку |
| Результат | eventually, дренаж ~5 минут |
| Ёмкость | ~30 подов, Kafka ~10 брокеров, Redis 8+8, Postgres 1+1 |

---

## 1. Требования

Выведены из ТЗ. Источник: **явно** — сказано в ТЗ, **выводимое** — следует из
сказанного, **наше** — решение команды.

| | Требование | Источник |
|---|---|---|
| FR-1 | Создать опрос: один вопрос, N вариантов, `single` или `multiple` | явно |
| FR-2 | Опрос доступен по короткой ссылке и QR | явно |
| FR-3 | Проголосовать анонимно, без регистрации | явно |
| FR-4 | Дедупликация: F5, закрытие вкладки, двойной клик | явно |
| FR-5 | Обезличенные результаты в админке | явно |
| FR-6 | Управление окном голосования | выводимое |
| FR-7 | Аутентификация админки | выводимое |
| FR-8 | Голоса вне окна отвергаются | выводимое |
| NFR-1 | Пик: 100 млн зрителей, окно 60 с | явно |
| NFR-2 | Доступность в окне эфира: второго шанса нет | выводимое |
| NFR-3 | Завышение недопустимо, потеря < 0.01 % приемлема | выводимое |
| NFR-4 | Связи «голос ↔ человек» нет в модели данных | явно |
| NFR-5 | Падение одного компонента не выводит систему из строя | наше |
| NFR-6 | У каждого компонента есть путь роста | наше |
| NFR-7 | Метрики, логи, трейсы в едином окне | наше |
| NFR-8 | Границы слоёв проверяются линтером | наше |
| NFR-9 | OWASP-базис, секреты вне кода, аудит админки | наше |

### Четыре наблюдения, определившие дизайн

**«Обезличенные результаты»** — требование к модели хранения, не к UI: связи
«голос ↔ человек» не должно существовать в принципе.

**«Не слишком защищённая от обхода»** — редкий случай, когда ТЗ ограничивает
сверху. Proof-of-work, fingerprinting, антифрод — вне скоупа.

**«Чтоб не накручивали»** задаёт асимметрию ошибок: про потерю голосов ТЗ
молчит, про накрутку — нет.

**«Результаты опроса»** без единого слова о свежести — ключевое наблюдение всей
задачи, см. §2.

### Допущения

| | Допущение | Значение | Если неверно |
|---|---|---|---|
| A-1 | Конверсия зрителей в голоса | 30 % | архитектура линейна: меняется число нод |
| A-2 | Форма нагрузки | 50 % в первые 15 с | меняется пиковый RPS, не дизайн |
| A-3 | Результаты нужны eventually | дренаж ~5 мин | сжатие дренажа дорожает по Redis |
| A-4 | Ожидаемая аудитория пер-опрос | `expected_audience` | ёмкость выводится функцией |
| A-5 | Регион | один | мультирегион — это CDN/edge |

### Вне скоупа

| Что | Почему |
|---|---|
| Антифрод, защита от технически подкованных | ТЗ: «не слишком защищённая от обхода» |
| Регистрация, профили, история голосований | противоречит анонимности |
| Несколько вопросов в опросе | ТЗ: «1 вопрос» |
| Свободный текст в ответах | нет агрегата, нет обезличивания |
| Аудит-трейл отдельных голосов | противоречит анонимности; пересчёт невозможен |
| Fingerprinting | 18 бит против 30 млн: потеря 99 %, отказы смещены по устройству |
| Голосование из другого браузера | отпечаток различает браузеры, а не устройства |

## 2. Шесть решений

| Решение | Почему |
|---|---|
| Голос — инкремент, не строка | нужен агрегат; 30 млн голосов = счётчики, не записи |
| Read-path целиком на CDN | опрос один для всех; иначе 30 млн запросов за одним JSON убьют origin |
| **В окне эфира — только приём** | ТЗ не требует свежести результата, значит дедуп и подсчёт могут быть после |
| **Kafka принимает, консьюмер считает** | отказ Redis становится задержкой, а не потерянным эфиром |
| Один атомарный Lua на голос | дедуп и инкремент вместе → корректность плюс идемпотентность |
| Ёмкость по расписанию опроса | событие короче петли обратной связи HPA |

Третье решение — ключевое. ТЗ говорит «посмотреть результаты опроса (админка)» и не задаёт времени. Единственное жёсткое требование в окне — **принять голоса и не потерять**. Всё остальное отложимо, и это меняет форму системы.

## 3. Нагрузка

| Сценарий | Конверсия | Голосов | Пик |
|---|---|---|---|
| На практике | 1 % | 1 млн | ~60k RPS |
| Оптимистично | 5 % | 5 млн | ~300k RPS |
| **Расчётный** | **30 %** | **30 млн** | **~2M RPS** |

Половина трафика — в первые 15 секунд: `15 млн / 15 с ≈ 1M RPS` средних, пик ~2M.

Конверсия не задана в ТЗ, поэтому это допущение — и оно **пер-опрос**: админ указывает `expected_audience`, ёмкость выводится функцией.

### Что доходит до origin

| Запрос | Кэш | На origin |
|---|---|---|
| `GET /p/{slug}` — страница | immutable, CDN | ~0 |
| `GET /api/v1/polls/{slug}` — вопрос | TTL 10 с, CDN | ~0 |
| `POST /api/v1/polls/{slug}/vote` | нет | **2M RPS** |

Одна некэшируемая ручка вместо двух. **Вес страницы — главная статья бюджета:** 30 млн загрузок, и CDN обходится дороже всего compute в семь раз (см. §12).

### Ёмкость

```
приём      разбор JSON + append в батч продюсера  →  ~100k RPS/под  →  ~30 подов
Kafka      2M msg/s × ~60 Б = 120 МБ/с            →  6–12 брокеров
дренаж     5 минут → 400k/с в Redis               →  8 мастеров + 8 реплик
дедуп      30 млн × ~100 Б ≈ 3 ГБ                 →  ~190 МБ на мастера
Postgres   единицы RPS, вне горячего пути
```

Дренаж — ручка «стоимость против задержки результата», линейная:

| Дренаж | Мастеров Redis | Результат готов |
|---|---|---|
| 60 с | 32 | T+1 мин |
| **5 мин** | **8** | **T+6 мин** |
| 15 мин | 3 | T+16 мин |

## 4. Архитектура

```
зритель → CDN ─┬─ страница, конфиг опроса (кэш)
               └─ POST /vote → LB → vote-api ×30 (stateless)
                                        │ produce, ~5 мс
                                   ┌────▼─────┐
                                   │  Kafka   │  партиции по voterID, retention 10 мин
                                   └──┬────┬──┘
                    counting-consumer │    │ fraud-consumer   (отдельный group.id)
                                      │    └──► fraud:{poll}:* агрегаты
                          EVALSHA ────▼
                                 Redis Cluster 8+8
                                      │ снапшот → финализация
                                 Postgres (primary + replica)
                                      │
                                   админка
```

| Слой | Что | Статус |
|---|---|---|
| L0 браузер | одна кнопка, случайный ID в `localStorage` | клиент |
| L1 CDN | статика и конфиг опроса | описан |
| L2 vote-api | валидация, rate limit, ASN, produce | реализуем |
| L3 Kafka | приём и развязка | реализуем |
| L4 консьюмеры | дедуп, подсчёт, анализ | реализуем |
| L5 Redis | дедуп-ключи и счётчики | реализуем |
| L6 Postgres | control plane и результаты | реализуем |

### Что Kafka даёт и чего стоит

| Даёт | |
|---|---|
| Отказ Redis становится задержкой | полный отказ на минуту = поздний результат, а не потерянный эфир |
| Отказ шарда невидим клиенту | `503` уходит из пользовательского пути вместе с брейкером и ретраями |
| Серверная метка времени | момент прихода доверенный → проверка окна точная, токены не нужны |
| Приём эластичнее Redis | последовательная запись с батчингом против однопоточного Lua |
| Fan-out для анализа | второй consumer group не может замедлить подсчёт |

| Стоит | |
|---|---|
| Ответ асинхронный | `202 accepted` вместо `counted`/`already_counted` |
| Ещё одна система в эксплуатации | брокеры, консьюмеры, продюсер на горячем пути |
| Retention — вопрос приватности | 10 минут делают её буфером, а не архивом |

Асинхронный ответ оказался не потерей: `already_counted` нужен был честному человеку с плохой сетью, а его случай закрыт — голос принят с первой попытки. Повторный визит обслуживает `localStorage`.

### Redis = data plane, Postgres = control plane

| | Data plane | Control plane |
|---|---|---|
| RPS | ~400k в дренаже | единицы |
| Данные | счётчики, эфемерный дедуп | опросы, пользователи, история |
| Жизнь | минуты | годы |

Postgres нужен ради вторичных индексов админки, транзакции «опрос + N опций + уникальный slug», холодных данных вне RAM, версионированной схемы и независимого носителя. Без админки он был бы не нужен.

### Пакеты

```
domain      Poll, правила выбора, FSM, агрегат, функция ёмкости    ни от чего
voter       хэширование клиентского ID солью опроса                domain
vote        Lua, деривация ключей, шардирование                    domain, Redis
producer    отправка в Kafka с серверной меткой                    domain
consumer    counting и fraud, две группы                           vote, storage
snapshot    Redis → Postgres, финализация, корректировка           storage
storage/pg  репозитории control plane                              pgx
auth        argon2id, JWT, RBAC                                    —
httpapi     публичная ручка, админка, middleware                   всё выше
capacity    /internal/capacity для KEDA                            domain, storage
observ.     OTel, метрики, логи, health                            —
```

## 5. Горячий путь

### Приём: без единого обращения к состоянию

```
1. rate limit по префиксу /64 (локальный LRU)
2. ASN-фильтр датацентров
3. MaxBytesReader 1 КБ + разбор JSON
4. cfg опроса из in-process кэша         окно, тип, min/max, соль
5. валидация выбора
6. voterID = HMAC-SHA256(poll.salt, clientID)[:16]
7. produce(Kafka, {pollID, voterID, choices, ts})
8. 202
```

Ни Redis, ни Postgres. Бюджет запроса — разбор крошечного JSON, один HMAC и append в батч.

### Подсчёт: один атомарный вызов на голос

```lua
-- KEYS[1] = v:{p:<pollID>:s<shard>}:<voterID>   маркер дедупа
-- KEYS[2] = c:{p:<pollID>:s<shard>}             хэш счётчиков
-- ARGV[1] = ttl, ARGV[2..] = индексы опций
if redis.call('SET', KEYS[1], '1', 'NX', 'EX', ARGV[1]) == false then
  return 0
end
for i = 2, #ARGV do redis.call('HINCRBY', KEYS[2], ARGV[i], 1) end
redis.call('HINCRBY', KEYS[2], 'b', 1)
return 1
```

**Идемпотентность здесь несущая, а не удобная.** Kafka доставляет at-least-once: при ребалансе группы или падении между обработкой и коммитом оффсета сообщение придёт повторно. Дедуп-ключ и есть idempotency key, поэтому дубль доставки безвреден. Без этого свойства каждый ребаланс завышал бы результат.

### Шардирование

```
shard = xxhash64(voterID) % poll.shard_count
tag   = {p:<pollID>:s<shard>}       → оба ключа в одном слоте, иначе CROSSSLOT
```

Ключ шардирования не выбирается: дедуп привязан к `voterID`, атомарность требует общего слота.

**`shard_count` не константа.** Перекос между мастерами равен `1/√(шардов на мастера)`:

| Шардов на мастера | 32 | 128 | 512 | 1024 |
|---|---|---|---|---|
| Перекос | ±17 % | ±8.8 % | ±4.4 % | ±3.1 % |

Правило `shard_count ≈ 500 × мастеров`, потолок 16384. Значение **фиксируется в строке опроса**: смена константы в дренаже перевела бы уже посчитанных на другие шарды и открыла повторный счёт.

### Consistent hashing не нужен

Redis Cluster делает то же лучше: 16384 слота — фиксированное пространство, отвязанное от числа нод, плюс явная таблица назначений. Наш `% shard_count` — константа fan-out, а не число нод.

Единственная связанная опасность — смена константы, и кольцо её не лечит, а лишь уменьшает долю сломанных с ~всех до 1/N. Для дедупа этого недостаточно.

### Партиционирование Kafka

По `voterID`: все сообщения одного голосующего попадают в одну партицию и обрабатываются по порядку. Корректность не пострадала бы и при случайном партиционировании — Lua атомарен, победит один, — но так чище и партиция соответствует шарду.

## 6. Дедупликация

### Ровно один вход

```
1. Браузер    voter = localStorage['v'] ?? crypto.randomUUID()      128 бит
2. Запрос     POST /vote {"choices":[2], "voter":"<uuid>"}
3. Сервер     voterID = HMAC-SHA256(poll.salt, voter)[:16]
4. Ключ       v:{p:<pollID>:s<shard>}:<hex(voterID)>   значение "1"
```

Значение — `"1"`, **не выбор**. Ключ доказывает факт голосования, но не содержание.

### Что сознательно не используем

| Признак | Почему нет |
|---|---|
| IP | за одним адресом оператора сотни тысяч зрителей (CGNAT) |
| Fingerprint | энтропии не хватает: при 30 млн массовые коллизии, отказы смещены по демографии |
| Cookie | эквивалент `localStorage`, но летит в каждом запросе — лишние байты при 30 млн |
| Аккаунт | регистрации нет по условию |

Про fingerprint подробнее, потому что соблазн велик. Мобильные отпечатки однороднее десктопных, а десктопные дают ~18 бит. При 262 тыс. различимых значений и 30 млн голосующих принят будет только первый из каждой группы: **потеря 99 %**. И отказы концентрируются на самых распространённых моделях, то есть смещены по доходу — в национальном опросе это испорченный результат, а не шум.

### Зачем хэшировать на сервере

ID генерит клиент, поэтому три вещи обязательны: длина ключа фиксирована независимо от присланного; чужой ключ не подобрать, соль неизвестна; между опросами связи нет — тот же браузер даёт несвязанные `voterID`.

### Инварианты

```
DEDUP_TTL ≥ окно дренажа × запас     ключ создаётся консьюмером, а не при приёме,
                                     и обязан пережить разрыв между первым и последним
                                     сообщением одного голосующего
джиттер TTL ±10 %                    иначе 30 млн ключей истекут одновременно
```

### Слои и чего они стоят обходить

| Слой | Механизм | Останавливает | Обходится |
|---|---|---|---|
| 0 | `localStorage` ID | F5, закрытие вкладки, двойной клик | инкогнито, очистка данных |
| 1 | хэширование солью опроса | подмену чужого ключа, связь между опросами | — |
| 2 | `SET NX` внутри Lua | повтор тем же ID, авторитетно | новым ID |
| 3 | rate limit частоты по /64 | наивный скрипт | прокси |
| 4 | ASN-фильтр датацентров | скрипт с VPS | резидентные прокси |

ТЗ просит «достаточную на уровне обычных пользователей» и явно не требует антифрода. Слои останавливают человека с F5 и инкогнито и не останавливают двадцать строк на Python.

**Kafka попутно улучшила два слоя.** Пропал оракул: каждый запрос возвращает `202`, и скрипт не узнаёт, какие голоса прошли. И порог лимита можно ужать — ретраев больше нет, честный голосующий делает ровно один запрос.

### Rate limit — три ошибки, которые легко сделать

| Ошибка | Последствие |
|---|---|
| Лимит количества, а не частоты | за CGNAT сотни тысяч человек — режем целевую аудиторию |
| Лимит по полному IPv6-адресу | у клиента /64, каждый запрос с нового → защиты нет |
| `X-Forwarded-For` как есть | обход одной строкой в curl |

### Анализ накрутки: категориальное автоматом, статистическое оператору

Сырой поток живёт в Kafka на время retention, поэтому **между приёмом и финализацией есть окно, в котором можно исключить голоса**. Раньше это было невозможно: счётчик инкрементился синхронно и назад не отматывался.

`fraud-consumer` отдельной группой считает агрегаты — вклад по /16, форму кривой прихода по подсети, разнообразие классов UA через HyperLogLog. Отдельная группа означает, что анализ **не может замедлить или сломать подсчёт**.

Автоматическое исключение по порогу **не делаем**. Легитимный трафик концентрирован по природе: одна `/16` крупного оператора законно приносит миллионы голосов, и порог отсёк бы крупнейшего оператора. Молча выбросить голоса региона в национальном опросе хуже, чем опубликовать завышенный результат и раскрыть это.

| Тип правила | Решение |
|---|---|
| Категориальное (датацентровый ASN) | автоматически, на приёме — адрес AWS по определению не зритель |
| Статистическое (аномальная подсеть) | сигналы в админке, исключение — явное действие с предпросмотром дельты и записью в аудит |

Порог появится, когда наберётся история нескольких эфиров и станет с чем сравнивать.

## 7. Данные

### Postgres

```sql
polls        (id, slug unique, question, type, min_choices, max_choices,
              status, opens_at, closes_at, shard_count,
              expected_audience, expected_conversion,
              salt bytea, version, created_at)
poll_options (poll_id, idx smallint, text)              -- PK (poll_id, idx)
poll_results (poll_id, option_idx, votes, updated_at)   -- PK, монотонная
poll_results_adjusted (poll_id, option_idx, votes, excluded_nets jsonb, at)
poll_stats   (poll_id, ballots_total, updated_at)
admin_users  (id, login unique, password_hash, role)
admin_audit  (id, actor, action, entity, payload jsonb, at)
```

Опция адресуется целым индексом, а не UUID: индекс становится полем хэша счётчиков в Redis, а payload голоса — `{"choices":[2]}`.

Проценты считаются от `ballots_total`, а не от суммы голосов: при множественном выборе сумма больше числа проголосовавших.

**Два набора результатов.** `poll_results` монотонна через `GREATEST` — это аудит процесса подсчёта. `poll_results_adjusted` считается один раз при финализации и является публикуемым результатом. Монотонность и исключение голосов несовместимы, поэтому разведены.

FSM: `draft → scheduled → open → closed → archived`. Статус хранится явно, не выводится из дат — иначе состояние зависит от часов машины.

### Redis

```
c:{p:<pollID>:s<shard>}          hash {"0":1249, "1":883, "b":2132}
v:{p:<pollID>:s<shard>}:<voter>  "1" с TTL и джиттером — дедуп
```

Ключа `agg:` нет: результаты читает админка из Postgres, единицы RPS. Пред-агрегация была нужна для свежести, которой ТЗ не требует.

### Как данные попадают в Postgres

Не поток и не очередь. Снапшотер **периодически пересчитывает полное состояние**: читает абсолютные значения, записывает абсолютные. Отсюда — пропущенный цикл догоняется следующим, порядок не важен, повтор безвреден.

```
каждые 30 с (свежесть не требуется):
  1. HGETALL по всем шардам, с реплик, одним пайплайном
  2. свёртка в памяти
  3. монотонность: max(посчитанное, последнее известное)   ← одно место
  4. UPSERT ... GREATEST → poll_results

при lag == 0 после closes_at:
  5. финальный снапшот
  6. применить исключения оператора → poll_results_adjusted
  7. status → closed
```

`GREATEST` даёт неожиданное: счётчики монотонны, значит два снапшотера одновременно безопасны, и лидер-элекшн становится оптимизацией, а не требованием корректности.

**Дедуп-ключи в Postgres не едут никогда.** Переносится только агрегат.

Направление строго одностороннее: Redis → Postgres для результатов, Postgres replica → память инстанса для конфига. Обратно ничего.

## 8. API

| Метод | Путь | Кэш | Заметки |
|---|---|---|---|
| `GET` | `/p/{slug}` | immutable | статика |
| `GET` | `/api/v1/polls/{slug}` | TTL 10 с | вопрос, опции, `server_time` |
| `POST` | `/api/v1/polls/{slug}/vote` | нет | единственная некэшируемая |
| `GET` | `/internal/capacity` | нет | для KEDA, не публичный |

`server_time` в конфиге — клиент работает по серверному времени, иначе сбитые часы ломают голосование.

### Ответы `/vote`

| Код | Тело | Когда |
|---|---|---|
| `202` | `{"status":"accepted"}` | голос принят в Kafka |
| `400` | `invalid_choices` | нарушены `min/max`, неверный индекс, битый `voter` |
| `409` | `poll_closed` | вне окна голосования |
| `403` | `blocked` | датацентровый ASN |
| `429` | — | rate limit |
| `503` | `Retry-After` | Kafka недоступна |

`202`, а не `200`: голос принят к обработке, засчитан он будет консьюмером. Отвечать `200 counted` за то, что ещё не посчитано, — это врать клиенту, и мы этого не делаем.

Админский API: `POST /admin/login`, `POST /admin/polls`, `GET /admin/polls`, `…/{id}/open`, `…/{id}/close`, `GET …/{id}/results`, `POST …/{id}/exclude`.

## 9. Отказоустойчивость

Требование: падение любого одного компонента не выводит систему из строя.

| Компонент | Экз. | Падение одного | Деградация |
|---|---|---|---|
| CDN PoP | сотни | трафик на соседний | нет |
| Балансировщик | managed, N зон | зона выпадает | нет |
| vote-api | ~30 | трафик перетекает | нет, stateless |
| Брокер Kafka | 6–12, RF=3 | лидер партиции переезжает за секунды | нет |
| Консьюмер | N | ребаланс группы | лаг растёт, голоса ждут |
| Redis master | 8 | реплика промотится ~8 с | **дренаж замедляется, потерь нет** |
| Postgres primary | 1+1 | failover | админка; приём и подсчёт идут |
| Fraud-consumer | 1 | — | нет сигналов накрутки, подсчёт цел |

**Единственный компонент, чей полный отказ останавливает приём, — Kafka.** Redis, Postgres, консьюмеры могут лежать: голоса ждут в логе.

Именно это Kafka и покупает. При синхронной записи в Redis полный отказ кластера означал потерянный эфир: клиенты ретраят ~25 секунд и уходят, а ролик заканчивается. С Kafka это поздний результат.

### Почему браузерный ретрай был недостаточен

```
простой шарда 8 с  →  затронуто 3 % от 30 млн = 930 тыс.
отказ человека ждать спиннер 8–10 секунд  →  20–40 %
потеря  →  0.6–1.2 %
```

Kafka сводит это к нулю: человек видит «спасибо» за пять миллисекунд, голос применяется позже.

### Managed Redis непригоден

ElastiCache делает failover за 60–120 секунд без SLA на RTO. Даже с Kafka впереди это задерживает дренаж на минуты; без неё означало бы потерянный эфир. **Self-hosted, не managed.**

### WAIT не берём

| Риск | Масштаб |
|---|---|
| Потеря незареплицированного при failover | ~62 голоса (lag × RPS шарда) |
| Замедление дренажа на 8 с | потерь нет, Kafka держит |

WAIT лечит первую строку — 0.0002 % — удваивая число мастеров, и гарантии не даёт: Redis не имеет консенсуса на запись. `cluster-node-timeout = 5000` вместо дефолтных 15000: простой ~8 с. Это отклонение от практики, риск — ложный failover; проверяется нагрузочным тестом.

### Валидация — тестом, не декларацией

| Сценарий | Ожидание |
|---|---|
| `make chaos-redis-master` | дренаж замедлился, **сумма счётчиков равна числу принятых `202`** |
| `make chaos-consumer` | ребаланс, дубли доставки не удвоили счёт |
| `make chaos-postgres` | приём и подсчёт идут, снапшоты возобновились |
| `make chaos-kafka-broker` | лидер переехал, ни одного `503` |

Каждый сценарий заканчивается проверкой корректности агрегата, а не «сервис отвечает».

## 10. Масштабируемость и узкие места

| Компонент | Ограничение | Масштабируется | Характер |
|---|---|---|---|
| CDN | — | managed | потолка нет |
| vote-api | syscalls, разбор JSON | горизонтально, stateless | линейно |
| Kafka | диск, сеть | партициями и брокерами | линейно |
| Консьюмеры | пропускная Redis | KEDA по consumer lag | линейно до потолка Redis |
| Redis | **однопоточный Lua** | добавлением мастеров | линейно |
| Postgres | вне горячего пути | вертикально + реплики | не узкое место |

**Главный потолок — однопоточность Lua**, 60–100k/с на мастера независимо от числа ядер. Но он больше не на пути запроса: он определяет длительность дренажа, а не доступность приёма.

Узкие места, названные заранее:

- **Логи и трейсы.** При 2M RPS запись на каждый запрос — терабайты. Сэмплирование это условие работы, не оптимизация.
- **Rate limiter.** LRU по десяткам млн префиксов — память. Размер таблицы ограничен явно.
- **Аллокации.** Лишняя аллокация на запрос — 2 млн/с давления на GC. `sync.Pool`, никаких лишних `string`↔`[]byte`.
- **Вес страницы.** Лишний КБ = 30 ГБ трафика за минуту и главная статья бюджета.
- **Партиции Kafka.** Число фиксируется заранее, как `shard_count`; увеличить в эфире нельзя.

## 11. Ёмкость по расписанию

### Почему автоскейлинг неприменим к приёму

| Этап петли HPA | Время |
|---|---|
| scrape + окно усреднения | ~45 с |
| sync loop | 15 с |
| rate limiter `100 %/15 с`: 10→20→40→80→160 | 60 с |
| провижининг нод | 40–120 с |

Минимум 60 секунд, реалистично 2–3 минуты. **Ролик длится 60 секунд, пик в первые 15.** Автоскейлер добавит мощности под трафик, которого уже нет.

Redis не масштабируется во время работы вовсе: миграция слота с миллионами ключей — 20–90 секунд, плюс `ASK`/`MOVED` на клиентах. Но **между эфирами keyspace пуст, и пересборка мгновенна** — то, что блокирует scale-up под нагрузкой, вне эфира ничего не стоит.

### Календарь уже в базе

```
capacity-advisor (read-only на polls) → GET /internal/capacity
        ↓
KEDA external scaler → vote-api, консьюмеры, StatefulSet Redis
Karpenter            → ноды под pending pods
```

Права на кластер остаются у KEDA. У нас — чистая функция от данных, покрытая табличным тестом.

| Фаза | Условие | Ёмкость |
|---|---|---|
| `idle` | ближайший опрос дальше часа | 2 пода |
| `prewarm` | T−60 Kafka · T−15 API · T−5 Redis и консьюмеры | нарастает ступенями |
| `live` | статус open | полная |
| `drain` | закрыт, `consumer lag > 0` | консьюмеры и Redis |
| `idle` | **`lag == 0`** | снос |

`lag == 0` — точный критерий сноса, а не таймаут: он означает, что все голоса доехали в Redis и снапшот финализирован. Здесь KEDA по размеру очереди работает ровно как задумано.

Ёмкость выводится из `expected_audience`, которую заполняет админ, а не из константы в коде. Валидация при создании: `opens_at` не раньше чем через час, иначе Kafka не успеет.

Асимметрия провижининга: **Kafka обязана быть поднята и проверена до эфира** — её отказ означает потерянный приём. Redis можно поднимать позже: его отказ задерживает дренаж, но не теряет голоса.

### Инженерия времени старта

Pause-поды держат ноды тёплыми и вытесняются мгновенно. Образ предзагружен. `readinessProbe` реально проверяет зависимости — иначе под встанет Ready и начнёт отдавать ошибки. Go стартует за миллисекунды, JIT-прогрева нет.

Риск, который вспоминают поздно: плановый scale-out предполагает, что ёмкость в зоне **есть**. Раскладывать по зонам, брать capacity reservation, поднимать за час, а не за пятнадцать минут.

## 12. Безопасность

| Область | Меры |
|---|---|
| Админка | argon2id, JWT с коротким TTL, RBAC, лимит попыток логина, аудит. Дефолтные креды при `ENV=production` — ошибка старта |
| Голосующий | соль опроса на сервере, валидация формата `voter`, отказ на константу |
| DoS | `MaxBytesReader` 1 КБ, `ReadHeaderTimeout` против Slowloris, `LimitListener` |
| Redis и Kafka | AUTH и TLS обязательны: незащищённый Redis отдаёт связь `voterID` ↔ выбор |
| Заголовки | HSTS, CSP с nonce, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, CORS по allowlist |
| XSS | текст вопроса и опций экранируется при рендере; они приходят от админа, но админ не доверенный источник разметки |
| CSRF | админский JWT в заголовке, не в cookie; `SameSite=Strict` там, где cookie всё же нужна |
| Сборка | `gosec`, `govulncheck`, Dependabot, distroless, non-root, read-only rootfs |

### Приватность: где она держится и где протекает

Держится: дедуп-ключ хранит факт голосования, но не выбор. `voterID` производен от случайного клиентского ID и соли опроса, между опросами не связывается. Отдельные голоса в Postgres не попадают никогда.

**Протекает в трёх местах, и это надо называть честно:**

| Канал | Окно |
|---|---|
| AOF Redis | эффекты Lua пишутся рядом: `SET v:…:<voterID>` и `HINCRBY c:… 2` |
| Kafka | сообщение содержит `voterID` и `choices` вместе, retention 10 минут |
| Наблюдение шарда | шард вычислим из `voterID`; снятие счётчика до и после выдаёт выбор |

Третий канал не лечится ни политикой, ни правами — он следствие шардирования по `voterID` ради атомарности.

**Формулировка гарантии:** связь «человек → выбор» не выводима из API и из Postgres; на уровне оператора Redis и Kafka она доступна в пределах retention и TTL. Меры: шифрование at-rest, `SLOWLOG` выключен, доступ по журналируемым правам, короткий retention.

## 13. Стоимость

Ключевое следствие расписания: между эфирами Redis и Kafka **уничтожаются**, а не масштабируются вниз — персистентного состояния нет ни там, ни там.

| | Постоянно на пике | По расписанию |
|---|---|---|
| Compute | ~$14 000/мес | ~$60/мес |
| CDN, 13 эфиров | — | ~$550/мес |
| Базовая линия | — | ~$250/мес |

```
один эфир:  CDN ~$42   ·   весь compute ~$4.5
```

**CDN — две трети всей стоимости.** После автоматизации расписания оптимизировать надо его:

| Рычаг | Эффект |
|---|---|
| CDN с плоским тарифом вместо per-GB | до −$40 за эфир |
| Страница 8 КБ → 4 КБ | −$10 за эфир |
| brotli вместо gzip | −15 % трафика |
| Не грузить QR в браузер зрителя | −запрос на человека |

На чём экономить не стоит: реплики Redis (экономия $10/мес, риск — 12 % голосов при отказе мастера без реплики) и spot для окна эфира (отзыв инстанса в момент ролика против экономии трёх долларов).

## 14. Наблюдаемость

Всё по OTLP в единое окно Grafana — `grafana/otel-lgtm` собирает Grafana, Prometheus, Loki, Tempo и Collector в одном контейнере.

| Сигнал | Транспорт |
|---|---|
| Метрики | OTel SDK → OTLP, плюс `/metrics` |
| Трейсы | OTel SDK → OTLP, `ParentBased(TraceIDRatioBased(0.0001))` |
| Логи | `slog` → OTel bridge → OTLP, плюс stdout JSON |
| Ошибки | structured error-логи + `errors_total{type}`; Sentry опционален |

При 2M RPS нельзя логировать и трейсить каждый запрос. Полноту даёт не лог, а метрики. Разрешение метрик — 5 секунд: при минутном окне дефолтные 60 дадут одну точку на весь эфир.

Дашборды в репозитории:

1. **Приём** — RPS, `202`/`4xx`/`5xx`, латентность produce, доля 429 по подсетям
2. **Дренаж** — consumer lag, скорость подсчёта, прогноз завершения
3. **Redis** — ops/s по нодам, `latest_fork_usec`, `aof_delayed_fsync`, **`evicted_keys` обязан быть 0**, распределение по шардам
4. **Накрутка** — вклад по /16, форма кривой прихода, разнообразие UA

Consumer lag превращается в честный элемент админки: «опрос закрыт, обработано 87 %, осталось ~40 секунд».

## 15. Корнер-кейсы

### Семь тихих отказов

Ломают корректность, не оставляя следа ни в тестах, ни в логах, ни на дашборде.

| Отказ | Последствие | Защита |
|---|---|---|
| `maxmemory-policy` ≠ `noeviction` | Redis вытесняет дедуп → повторы идут в счёт | конфиг + алерт `evicted_keys > 0` |
| `DEDUP_TTL` меньше окна дренажа | ключ истёк между сообщениями одного человека | инвариант в тесте и на старте |
| Integration-тесты на одиночном Redis | `CROSSSLOT` не воспроизводится, падает в проде | testcontainers поднимает **кластер** |
| `sessionStorage` вместо `localStorage` | F5 работает, закрытие вкладки даёт новый голос | тест эмулирует закрытие, а не перезагрузку |
| Rate limit по полному IPv6 | у клиента /64 — защиты нет, метрика зелёная | лимит по префиксу |
| `X-Forwarded-For` без доверенного прокси | обход одной строкой в curl | только hop от своего ingress |
| Лавинное истечение TTL | active expiry молотит на хвосте дренажа | джиттер ±10 % |

### Клиент

| Кейс | Решение |
|---|---|
| Двойной клик | два сообщения в Kafka, дедуп в консьюмере, счёт верен |
| Таймаут сети | ретрай тем же `voter` из `localStorage`, идемпотентно |
| Часы клиента врут | работа по `server_time` |
| Safari private / ITP | `localStorage` бросает — всё в try/catch |
| Webview мессенджера | часто нет storage → новый голос, by design |
| JS отключён | осмысленный `<noscript>` |
| bfcache при «назад» | проверка на `pageshow` |
| Инкогнито | новый ID, голос засчитан — by design |

### Kafka и консьюмеры

| Кейс | Решение |
|---|---|
| Дубль доставки при ребалансе | Lua идемпотентен по `voterID` |
| Голос произведён на 59-й секунде, обработан на 300-й | окно проверяется по серверной метке produce, не по времени обработки |
| Консьюмер отстал | лаг виден, ёмкость скейлится KEDA |
| Партиция без лидера | продюсер ретраит, `acks=all` |
| Порядок сообщений одного человека | партиционирование по `voterID` |

### Redis, агрегация, админка

| Кейс | Решение |
|---|---|
| Failover на пике дренажа | консьюмер ретраит, дренаж замедляется |
| Split-brain | `full-coverage no`: теряется доля шардов, не весь опрос |
| `NOSCRIPT` после failover | rueidis фоллбэчит на `EVAL` |
| Ошибка в середине Lua | отката нет: дедуп есть, счётчик нет. Причина одна — OOM, см. `noeviction` |
| Два снапшотера одновременно | `GREATEST` делает безопасным |
| Правка опций после первого голоса | запрещена — меняет смысл поданных голосов |
| Два админа редактируют | optimistic locking по `version` |
| Исключение подсети после публикации | `poll_results_adjusted` пересчитывается, аудит хранит кто и почему |

## 16. Трейд-оффы

| Развилка | Выбор | Чем платим |
|---|---|---|
| Синхронный подсчёт vs Kafka | **Kafka** | асинхронный ответ, ещё одна система |
| Свежесть результата | **eventually, дренаж 5 мин** | результат на T+6 мин |
| Две ручки vs одна | **одна** | нет доказуемого времени выдачи — заменено меткой Kafka |
| Дедуп в памяти vs Redis | **Redis** | зависимость в консьюмере, не в запросе |
| Атомарность vs раздельные хранилища | **атомарность** | дедуп и счётчики делят память кластера |
| `cluster-require-full-coverage` | **no** | теряем долю шардов вместо всего опроса |
| `WAIT` | **нет** | ~62 голоса при failover |
| `cluster-node-timeout` | **5 с** | риск ложного failover, проверяется тестом |
| Persistence Redis | **AOF everysec** | rewrite отключён в окне |
| Аудит-трейл голосов | **нет** | пересчёт через неделю невозможен; исключение во время дренажа — можно |
| Дедуп: точный vs Bloom | **точный** | 3 ГБ вместо 54 МБ, зато ноль ложных отказов |
| Fingerprint | **нет** | −один сигнал; энтропии не хватает, отказы смещены |
| Исключение накрутки | **сигналы автоматом, решение оператору** | нужен человек в контуре во время эфира |
| `shard_count` | **≈500 × мастеров** | подбирается при создании опроса |
| Трейсинг всех запросов | **сэмпл 0.01 %** | единичный сбой может не попасть |
| Managed vs self-hosted Redis | **self-hosted** | своя эксплуатация |
| k8s-манифесты в репозитории | **нет** | рассуждение вместо непроверенного YAML |

## 17. Поддерживаемость

```
domain  ◄──  application  ◄──  adapters (httpapi, storage, producer, consumer)
```

`domain` не импортирует ничего из проекта. Обратные импорты запрещены **линтером** (`depguard`), не соглашением.

| Что | Правило |
|---|---|
| Конструкторы | `New*(deps…) (*T, error)`, зависимости параметрами, без глобалов и `init()` |
| Ошибки | типизированные доменные, **единственная** точка маппинга в HTTP |
| Логи | `slog`, общий набор атрибутов, `trace_id` везде |
| Контекст | `ctx` первым, таймаут на каждом внешнем вызове |
| Интерфейсы | на стороне потребителя, узкие |
| Конфиг | одна структура с тегами, валидация при старте, fail fast |

CI: `golangci-lint` v2, `govulncheck`, `go test -race`, порог покрытия. Тесты table-driven, имена читаются как утверждения.

## 18. Что осознанно не покрыто

- **Накрутку резидентными прокси не останавливаем.** По ТЗ и не должны. Обнаруживается агрегатами по подсетям; порядок цены меняет только Turnstile, и это зависимость от Cloudflare.
- **Пересчёт через неделю невозможен** — следствие отказа от аудит-трейла. Исключение во время дренажа доступно.
- **Real-time на студийном экране** потребовал бы синхронного подсчёта и вдвое большего Redis.
- **Мультирегиональность** — один регион; глобальное распределение это L1/CDN.
- **Прод-деплой** — стенд на docker-compose, KEDA и Karpenter описаны, но манифестов нет.


Порядок старта детерминирован через `service_healthy` и `service_completed_successfully`. Хост-порты через `${VAR:-default}`.

```
make demo    поднять всё, создать опрос, напечатать ссылки
make smoke   end-to-end проверка
make load    k6
make chaos   сценарии отказов
make test    unit + integration на Redis Cluster и Kafka
```

### Smoke доказывает главное требование

```
1. создать опрос через админку
2. проголосовать на vote-api-1     → 202
3. тем же voter на vote-api-2      → 202  (дедуп асинхронный)
4. дождаться lag == 0
5. /admin/results                  → ровно ОДИН голос   ← доказательство дедупа
6. голос после closes_at           → 409
7. голос с датацентрового IP       → 403
```

Пятый шаг доказывает, что дедуп не зависит от инстанса — то, ради чего он живёт в Redis.

### Нагрузочный тест

Ноутбук не выдаст 2M RPS. k6 меряет **стоимость одного голоса**: CPU-мс на под, байт по сети, аллокаций, команд в Redis на дренаже. Из неё ёмкость считается линейно.

Плюс проверка корректности: **сумма счётчиков после дренажа равна числу ответов `202` минус дубли.** Тест на латентность такую потерю не увидел бы.
