# Как менялись решения

Хронология проектирования. Каждая строка — момент, где следующий вопрос менял
предыдущий ответ.

| Вопрос | Что изменилось |
|---|---|
| Какая конверсия? | В ТЗ её нет. Сначала 5 %, потом по требованию 30 % — и допущение уехало в поле опроса, а не в константу |
| Что если Redis упадёт? | Серверный буфер → синхронный ретрай → Kafka. Первое решение врало клиенту, второе теряло голоса при отказе людей ждать |
| Зачем конфиг в Redis? | Незачем: 50 запросов в секунду к реплике Postgres, зато без двойной записи |
| Персистентность Redis тормозит? | Оценка была на монолитный Redis. При шардировании `fork` почти бесплатен, а AOF нужен ради дедупа |
| Почему две ручки? | Аргумент не выдержал пересчёта: накрутка стоит столько же, а приём вдвое дороже |
| Fingerprint не поможет? | Не поможет: 18 бит против 30 млн, и отказы смещены по демографии |
| Нужна ли Kafka? | Сначала «нет, она про аудит». Потом — «а если человек не станет ждать спиннер?» — и это перевесило |
| Результат нужен сразу? | **В ТЗ этого нет.** Ключевой вопрос всей задачи: Redis уменьшился вчетверо, поды втрое |
| Как экономить ночью? | Между эфирами Redis и Kafka уничтожаются: персистентного состояния нет. И CDN оказался дороже всего compute в семь раз |
| Автоскейлинг? | К приёму неприменим (событие короче петли), к консьюмерам применим — Kafka сдвинула дедлайн с 60 секунд до пяти минут |
