# Отчёт нагрузочного теста

Прогон на локальном стенде, 8 сентября 2026.

## Железо и топология

| | |
|---|---|
| Машина | MacBook Pro, Apple Silicon, Docker Desktop |
| Инстансы приёма | 2 (`app-1`, `app-2`) за nginx |
| Kafka | 1 брокер, KRaft, топик `votes`, 6 партиций |
| Redis | кластер 3 мастера + 3 реплики, AOF everysec |
| Postgres | 1 инстанс |
| Всё вместе | 13 контейнеров на одном ноутбуке |

Генератор нагрузки работает **в том же Docker**, деля CPU с сервисом. Это
занижает результат и завышает латентность — цифры ниже надо читать как нижнюю
границу, а не как потолок.

## Результат

```
принято на входе        30 250
посчитано после дренажа 30 250
отвергнуто                   0
сверка                  сходится — потерь в пайплайне нет

достигнутый RPS         ~500 (ограничен генератором, не сервисом)
латентность приёма      p50 489 мкс · p90 724 мкс · p95 851 мкс · max 6 мс
```

**Главное здесь не RPS, а первые три строки.** Потерю в пайплайне
«приём → Kafka → консьюмер → Redis → снапшот → Postgres» тест на латентность не
увидел бы никогда: все запросы вернули бы 202, а голоса тихо не доехали бы.

## Что тест нашёл

Первый прогон дал расхождение: 30 207 принято против 30 183 посчитанных, и в
логах консьюмера — `reason=unknown_poll`.

Причина оказалась настоящим дефектом, а не погрешностью. Приём и подсчёт живут
в разных процессах с независимыми кэшами конфигов. Голос принимал инстанс,
который про свежесозданный опрос уже знал, а консьюмер на другом инстансе ещё
не обновился — и отбрасывал сообщение, **закоммитив оффсет**. Голос исчезал
навсегда, без единой ошибки на стороне клиента.

Исправлено: при промахе кэша консьюмер ждёт появления конфига в пределах
бюджета, а не отбрасывает сообщение сразу. Бюджет ограничен, иначе чужое
сообщение держало бы партицию и дренаж не закончился бы никогда.

Второй дефект нашёлся там же — в самой проверке. Она опрашивала результаты
чаще, чем снапшотер обновляет агрегат, получала три одинаковых чтения внутри
одного цикла и объявляла дренаж законченным раньше времени. То есть сообщала о
потере, которой нет. Тест, врущий про потерю, хуже отсутствующего теста —
интервал опроса теперь заведомо больше интервала снапшота.

## Как эти цифры переносятся в прод

Абсолютный RPS ноутбука не переносится. Переносится стоимость единицы работы.

Приём одного голоса — это разбор ~80 байт JSON, один HMAC-SHA256 и запись в
батч продюсера. Ни Redis, ни Postgres на этом пути нет вовсе, поэтому
латентность определяется CPU и сетевыми syscalls, а не хранилищами. Медиана
в 489 мкс на машине, где генератор нагрузки конкурирует с сервисом за те же
ядра, подтверждает расчёт из `docs/design.md` §3: **порядка 30 подов на 2M RPS**.

Потолок Redis тест не проверяет и проверить не может — на трёх мастерах в
Docker он недостижим. Он остаётся расчётным: 60–100k `EVALSHA`/с на мастера,
отсюда 8 мастеров на дренаж за пять минут.

## Что осталось непроверенным

| | Почему |
|---|---|
| Реальный пик 2M RPS | нужен кластер, а не ноутбук |
| Потолок Lua в Redis | недостижим на трёх мастерах в Docker |
| Поведение при failover мастера | отдельный сценарий `make chaos` |
| Ложные failover при `cluster-node-timeout 5000` | требует продолжительного прогона на реальной сети |

## Воспроизведение

```bash
make demo
make load                 # PEAK_RPS=800 по умолчанию
PEAK_RPS=2000 make load   # выше — упрётся в генератор
```

На стенде `RATE_LIMIT_PER_MIN` поднят намеренно: весь трафик k6 приходит из
одной docker-сети, то есть с одного адреса, и продовый порог отверг бы тест
целиком — измерялся бы лимитер, а не сервис. В проде порог обратный: он
рассчитан на CGNAT, за которым сидят сотни тысяч живых зрителей.
