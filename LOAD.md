# Отчёт нагрузочного теста

Прогон на локальном стенде, 8 сентября 2026.

## Топология

| | |
|---|---|
| Машина | MacBook Pro, Apple Silicon, Docker Desktop |
| Приём | 2 × `televote-api` за nginx |
| Подсчёт | 2 × `televote-consumer` |
| Снапшоты | 1 × `televote-snapshot` |
| Kafka | 1 брокер, KRaft, топик `votes`, 6 партиций |
| Redis | кластер 3 мастера + 3 реплики, AOF everysec |
| Postgres | 1 инстанс |

Генератор нагрузки работает в том же Docker и делит CPU с сервисом. Цифры ниже
— нижняя граница, а не потолок.

## Результат

```
принято на входе        19 000
посчитано после дренажа 19 000
отвергнуто                   0
сверка                  сходится — потерь в пайплайне нет

достигнутый RPS         ~310 (ограничен генератором, не сервисом)
латентность приёма      p50 0.5 мс · p95 0.9 мс · p99 1.6 мс
```

Главное здесь не RPS, а первые три строки. Потерю в пайплайне «приём → Kafka →
консьюмер → Redis → снапшот → Postgres» тест на латентность не увидел бы: все
запросы вернули бы 202, а голоса тихо не доехали бы.

## Что тест нашёл

**Потерянные голоса.** Первый прогон дал 30 207 принятых против 30 183
посчитанных, в логах консьюмера — `reason=unknown_poll`. Приём и подсчёт живут
в разных процессах с независимыми кэшами конфигов: голос принимал инстанс,
который про свежесозданный опрос уже знал, а консьюмер ещё не обновился — и
отбрасывал сообщение, закоммитив оффсет. Голос исчезал без единой ошибки у
клиента. Исправлено: при промахе кэша консьюмер ждёт конфиг в пределах бюджета.
Бюджет ограничен, иначе чужое сообщение держало бы партицию бесконечно.

**Тест, врущий про потерю.** Проверка опрашивала результаты чаще, чем снапшотер
обновляет агрегат, получала три одинаковых чтения внутри одного цикла и
объявляла дренаж законченным раньше времени. Интервал опроса теперь заведомо
больше интервала снапшота.

**Ложный отказ на старте.** `setup` ждал появления опроса через балансировщик,
получал 200 с одной реплики и начинал слать голоса — часть попадала на вторую,
которая опрос ещё не видела. Теперь ждём каждый инстанс поимённо.

## Как эти цифры переносятся в прод

Абсолютный RPS ноутбука не переносится. Переносится стоимость единицы работы.

Приём одного голоса — разбор ~80 байт JSON, один HMAC-SHA256 и запись в батч
продюсера. Ни Redis, ни Postgres на этом пути нет, поэтому латентность
определяется CPU и сетевыми syscalls, а не хранилищами. Медиана 0.5 мс на
машине, где генератор конкурирует с сервисом за те же ядра, подтверждает
расчёт из README: порядка 30 подов на 2M RPS.

Потолок Redis тест не проверяет и проверить не может — на трёх мастерах в
Docker он недостижим. Он остаётся расчётным: 60–100k `EVALSHA`/с на мастера.

## Что осталось непроверенным

| | Почему |
|---|---|
| Реальный пик 2M RPS | нужен кластер, а не ноутбук |
| Потолок Lua в Redis | недостижим на трёх мастерах в Docker |
| Ложные failover при `cluster-node-timeout 5000` | требует долгого прогона на реальной сети |

Отказ мастера Redis, ребаланс консьюмеров и падение Postgres проверяет
`make chaos` — каждый сценарий заканчивается сверкой агрегата.

## Воспроизведение

```bash
make demo
make load                 # PEAK_RPS=500 по умолчанию
PEAK_RPS=2000 make load   # выше — упрётся в генератор
```

На стенде `RATE_LIMIT_PER_MIN` поднят намеренно: весь трафик k6 приходит из
одной docker-сети, то есть с одного адреса, и продовый порог отверг бы тест
целиком — измерялся бы лимитер, а не сервис.
