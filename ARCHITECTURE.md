# Обоснование архитектуры

Документ отвечает на вопрос «почему так, а не иначе». Подробный дизайн с
расчётами — [`docs/design.md`](docs/design.md), требования и допущения —
[`docs/requirements.md`](docs/requirements.md).

## Задача в числах

| | |
|---|---|
| Зрителей | 100 млн |
| Окно голосования | 60 секунд |
| Конверсия | **в ТЗ не задана** — расчёт под 30 % |
| Пик приёма | ~2M RPS |

Конверсия — главное числовое допущение, и оно вынесено в поле опроса, а не
зашито константой. Ошибка в нём меняет число нод, а не решения.

---

## Решение, определившее всё остальное

**ТЗ не требует, чтобы результат был виден сразу.** Формулировка — «посмотреть
результаты опроса (админка)», без единого слова о свежести.

Значит в окне эфира жёстко требуется ровно одно: **принять голоса и не
потерять**. Дедуп, подсчёт и агрегация отложимы.

Из этого следует форма системы:

```
приём (60 с)            →  Kafka  →  подсчёт (дренаж ~5 мин)  →  результат
2M RPS, без хранилищ                 400k/с в Redis
```

Что это дало:

| | Синхронный подсчёт | Приём в Kafka |
|---|---|---|
| Redis | 32 мастера | **8** |
| Поды приёма | ~100 | **~30** |
| Полный отказ Redis на минуту | **потерянный эфир** | поздний результат |
| Ответ клиенту | `counted` / `already_counted` | `202 accepted` |

Проверено на стенде: при остановленном мастере Redis приём продолжался, и все
голоса были посчитаны после его возврата (`make chaos`).

---

## Почему голос — это инкремент, а не строка

Бизнесу нужен обезличенный агрегат. Значит 30 млн голосов — это не 30 млн
записей, а счётчики по числу вариантов.

Побочный эффект оказался важнее экономии: **отдельных голосов нет нигде**, и
связь «человек → выбор» невозможно восстановить не потому, что мы обещали, а
потому, что её негде взять.

Цена: пересчитать результат через неделю нельзя. Исключить подсеть во время
дренажа — можно, потому что сырой поток ещё жив в Kafka.

## Почему один атомарный Lua-вызов

```lua
if redis.call('SET', KEYS[1], '1', 'NX', 'EX', ARGV[1]) == false then return 2 end
for i = 2, #ARGV do redis.call('HINCRBY', KEYS[2], ARGV[i], 1) end
redis.call('HINCRBY', KEYS[2], 'b', 1)
```

Дедуп и инкремент в одной операции дают четыре свойства сразу: корректность при
любой балансировке, отсутствие гонки «дедуп есть, счётчик нет», один RTT вместо
двух и — главное — **идемпотентность**.

Идемпотентность здесь несущая, а не приятная. Kafka доставляет at-least-once:
ребаланс группы переигрывает сообщения, и без неё каждый ребаланс завышал бы
результат. Проверено сценарием `chaos/consumer.sh`.

## Почему ключи шардируются по `voter_id`

Дедуп-маркер по природе привязан к голосующему, а атомарность требует, чтобы
счётчик лежал с ним в одном слоте Redis Cluster. Отсюда общий hash tag
`{p:<pollID>:s<shard>}` — без него `EVALSHA` возвращает `CROSSSLOT`, и голос не
будет ни посчитан, ни отвергнут: он просто пропадёт.

Consistent hashing не нужен: Redis Cluster решает ту же задачу лучше — 16384
слота образуют фиксированное пространство, отвязанное от числа нод.

## Почему автоскейлинг здесь неприменим

Петля HPA — от 60 секунд до трёх минут: scrape, усреднение, sync loop,
rate limiter, провижининг нод, старт пода. **Ролик длится 60 секунд, пик — в
первые 15.** Автоскейлер добавит мощности под трафик, которого уже нет.

Redis не масштабируется под нагрузкой вовсе: миграция слота с миллионами
ключей идёт десятки секунд.

Вместо автоскейлинга — **ёмкость по расписанию опроса**. Календарь уже лежит в
базе: `opens_at` известен заранее, ёмкость выводится из `expected_audience`
чистой функцией, а KEDA скейлит по её ответу.

Приятная асимметрия: между эфирами Redis и Kafka **уничтожаются целиком** —
персистентного состояния нет ни там, ни там. То, что блокирует scale-up под
нагрузкой, на пустом кластере ничего не стоит.

## Почему self-hosted Redis, а не managed

ElastiCache делает автоматический failover за 60–120 секунд без SLA на RTO.
**Наш эфир длится 60 секунд.** Даже с Kafka впереди это задерживает дренаж на
минуты; без неё означало бы потерянный эфир.

Это ограничение, а не предпочтение.

## Почему нет fingerprint

Соблазн велик: он закрыл бы инкогнито и очистку данных. Не работает по
арифметике.

Browser fingerprint даёт около 18 бит энтропии, у мобильных устройств меньше.
При 262 тыс. различимых значений и 30 млн голосующих правило «один голос на
отпечаток» приняло бы **262 тысячи голосов из 30 миллионов**.

Хуже, что отказы не случайны: они концентрируются на самых распространённых
моделях, то есть смещены по доходу. В национальном опросе это испорченный
результат, а не шум.

Кросс-браузерный отпечаток эту проблему усугубляет: свойство «различать
устройства, а не браузеры» дают ровно те сигналы, у которых меньше всего
энтропии — модель, версия ОС, GPU.

## Почему нет аудит-трейла отдельных голосов

Он дал бы возможность пересчитать результат, если его оспорят. И он же создал
бы хранилище персональных данных, противоречащее заявленной анонимности.

Выбрана анонимность. Следствие названо прямо: **результат неоспорим и
неисправим**. Частично компенсируется тем, что сырой поток жив в Kafka на время
retention, и во время дренажа подсеть можно исключить с предпросмотром дельты.

## Ключевые трейд-оффы

| Развилка | Выбор | Чем платим |
|---|---|---|
| Синхронный подсчёт vs Kafka | **Kafka** | асинхронный ответ, ещё одна система |
| Свежесть результата | **eventually, ~5 мин** | результат на T+6 мин |
| Две ручки vs одна | **одна** | нет доказуемого времени выдачи — заменено меткой Kafka |
| Дедуп в памяти vs Redis | **Redis** | зависимость в консьюмере, не в запросе |
| Аудит-трейл | **нет** | пересчёт невозможен |
| Fingerprint | **нет** | −один сигнал; энтропии не хватает |
| Managed vs self-hosted Redis | **self-hosted** | своя эксплуатация |
| `cluster-node-timeout 5s` | **против практики в 15 с** | риск ложного failover; проверяется тестом |
| Автоматическое исключение накрутки | **нет, решает оператор** | нужен человек в контуре |
| k8s-манифесты | **нет** | рассуждение вместо непроверенного YAML |

## Технологии

| Задача | Выбор | Почему именно он |
|---|---|---|
| Язык | Go 1.26 | дешёвые горутины, предсказуемый GC на мелких аллокациях, старт за миллисекунды без JIT-прогрева |
| Приём | `twmb/franz-go` | активно поддерживается, идиоматичен, хорошо работает с KRaft |
| Redis | `redis/rueidis` | auto-pipelining конкурентных запросов и мультиплексирование соединений — батчинг и защита от connection storm достаются бесплатно |
| Postgres | `jackc/pgx/v5` | нативный протокол вместо `database/sql` |
| Роутер | `go-chi/chi` | stdlib-совместимый, без магии |
| Наблюдаемость | OpenTelemetry → `grafana/otel-lgtm` | метрики, логи и трейсы одним контейнером на стенде |

**Не написано своими руками:** пайплайнинг Redis, `EVALSHA`/`NOSCRIPT` fallback,
батчинг продюсера, пул соединений, rate limiter, argon2, graceful shutdown.

**Написано:** Lua-скрипт голосования, вывод `voterID` солью опроса, шардирование
ключей, снапшотер, функция ёмкости. Это бизнес-логика, готового нет.

## Что осталось непроверенным

| | Почему |
|---|---|
| Реальные 2M RPS | нужен кластер, а не ноутбук; ёмкость считается линейно из стоимости голоса |
| Потолок Lua в Redis | недостижим на трёх мастерах в Docker |
| Ложные failover при `node-timeout 5s` | требует долгого прогона на реальной сети |
| Прод-деплой | KEDA и Karpenter описаны, манифестов нет — непроверенный YAML хуже отсутствующего |
